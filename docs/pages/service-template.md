# Общий шаблон коммерческой страницы услуги

## Статус

Рабочий шаблон для прототипирования внутренних коммерческих страниц A1.
Шаблон фиксирует обязательные пользовательские функции и общие компоненты, но не
требует одинаковых секций и одинакового текста на всех услугах.

Кандидат в эталон текущего этапа — `prototype/razrabotka-sajtov/index.html`.
Его полная последовательность контента и план утверждены, а собранная реализация
ожидает просмотра.

## Задача шаблона

- быстро объяснить предложение и результат услуги;
- помочь посетителю понять, подходит ли ему услуга;
- показать состав или варианты решения;
- подтвердить компетенции релевантными кейсами;
- объяснить процесс, границы, стоимость или принцип расчёта;
- привести к понятному следующему действию;
- связать родительскую услугу с самостоятельными дочерними интентами.

## Общий каркас

1. Первый экран: `h1`, вводный текст, основной CTA и релевантные доказательства.
2. Проблема клиента и уникальный подход A1.
3. Сервис-специфичный модуль выбора:
   - для разработки — виды сайтов;
   - для SEO — направления работ;
   - для рекламы — каналы и сценарии;
   - для CRM — платформы и процессы.
4. Кейсы и результаты, относящиеся к конкретной услуге.
5. Процесс, результат этапов и границы работ.
6. Цена, диапазон или принцип расчёта.
7. Снятие возражений.
8. Связанные услуги и материалы.
9. Финальный CTA.

Первый экран, подход, выбор решения, доказательства, условия и следующий шаг —
обязательные функции полной страницы. Они могут объединяться внутри разных
компонентов. FAQ, команда, отзывы, сертификаты, технологии, калькулятор,
отрасли и локальные доказательства добавляются только при содержательной
необходимости.

Если для будущего обязательного модуля нет утверждённого текста, это не разрешает
его придумывать. Модуль получает статус `pending` в page brief, а видимая
реализация заканчивается на последнем согласованном блоке.

## Источники и изменяемые поля

Для каждой услуги обязателен собственный page brief. В нём фиксируются:

- задача, аудитория, интент и география;
- дословный утверждённый видимый текст;
- рабочие цены, сроки, показатели и кейсы;
- CTA и его адрес;
- сервис-специфичный модуль;
- внутренние ссылки;
- готовые, опциональные и ожидающие контента блоки.

Общие компоненты шапки и футера можно повторно использовать только с текстом,
разрешённым page brief. HTML страницы не становится источником текста.

## URL и SEO-границы

В brief раздельно хранятся:

- технический путь прототипа;
- гипотеза production URL;
- статус SERP-исследования;
- статус canonical.

Технический путь статического прототипа не утверждает production URL, canonical,
редиректы или индексируемую структуру.

Родительская услуга помогает выбрать решение. Дочерняя или городская страница
создаётся только при отдельном интенте, собственном brief и самостоятельном
содержании. Нельзя автоматически размножать комбинации «тип × CMS × город».

## Техническая основа

- чистые HTML и CSS, небольшой vanilla JS только при необходимости;
- общие `styles.css`, `service.css` и `script.js`;
- если внутренняя страница задаёт общий `<base>`, пути к изображениям и другим
  ассетам указываются относительно него без дополнительного `../`;
- содержательный HTML доступен без обязательного JavaScript;
- один `h1`, последовательная иерархия `h2`–`h3`;
- вводный текст всегда находится под заголовком раздела;
- вводная фраза перед списком, заканчивающаяся двоеточием, визуально выделяется
  полужирным; её текст не сокращается и не превращается в отдельный заголовок;
- раскрытия доступны с клавиатуры и не конфликтуют с переходами по ссылкам;
- прогрессивное раскрытие применяется только к длинной детализации: основное
  предложение, варианты, цены, результаты, условия и CTA остаются видимыми;
- для последовательного процесса в закрытом состоянии видны название и результат
  этапа; несколько этапов можно открыть одновременно;
- FAQ использует независимые нативные `details`, если пользователь не утвердил
  другое поведение;
- desktop и mobile используют одинаковый порядок контента.

## Критерии готовности экземпляра

- page brief согласован до реализации;
- предложение и следующий шаг понятны на первом экране;
- сервис-специфичный модуль помогает принять решение;
- показаны только релевантные доказательства;
- рабочие данные явно зафиксированы в brief;
- нет видимых служебных заметок и неподтверждённых подводок;
- длинная страница остаётся сканируемой без скрытия ключевых коммерческих условий;
- навигационные гипотезы не выдаются за утверждённую production-архитектуру.
