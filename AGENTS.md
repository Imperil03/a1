# A1: правила работы с SEO-прототипом

## 1. Назначение проекта

Мы проектируем будущий сайт локальной веб-студии A1 для передачи дизайнеру и дальнейшего SEO-продвижения в Сургуте и Тюмени.

Результат текущего этапа — не финальный дизайн и не production-сайт. Это содержательный прототип: структура страниц, порядок блоков, тексты, сценарии, CTA, локальные сигналы, перелинковка и пояснения для дизайнера.

## 2. Текущий статус

- `prototype/index.html` — пересобранная главная на чистом HTML по утверждённой структуре.
- `prototype/styles.css` — стили главной в визуальном языке первой версии.
- `prototype/service.css` — общий слой компонентов коммерческих страниц услуг.
- `prototype/seo.css` — только индивидуальная композиция центральных SEO-блоков.
- `prototype/context.css` — только индивидуальная композиция центральных блоков
  контекстной рекламы.
- `prototype/complex.css` — только индивидуальная композиция центральных блоков
  комплексного интернет-маркетинга.
- `prototype/about.css` — индивидуальная редакционная композиция страницы
  «О компании».
- `prototype/blog.css` — общий редакционный слой каталога блога, детальной
  статьи и профилей авторов.
- `prototype/script.js` — только поведение меню, раскрывающихся элементов и других доступных интерфейсных состояний.
- `prototype/razrabotka-sajtov/index.html` — первый экземпляр общего шаблона услуги.
- `prototype/seo/index.html` — второй экземпляр системы услуг, страница SEO-продвижения.
- `prototype/kontekstnaya-reklama/index.html` — третий экземпляр системы услуг,
  страница контекстной рекламы.
- `prototype/complex-marketing/index.html` — четвёртый экземпляр системы услуг,
  страница комплексного интернет-маркетинга.
- `prototype/company/about/index.html` — самостоятельная страница «О компании»,
  не использующая последовательность шаблона услуг.
- `prototype/blog/index.html` — каталог экспертных материалов с тематическими
  фильтрами.
- `prototype/blog/neyroseti-v-seo/index.html` — эталонная детальная статья с
  закреплёнными в пределах главы заголовками.
- `prototype/blog/authors/anna-ivanova/index.html` — профиль автора с крупным
  портретом, опытом, специализацией и созданными материалами.
- `prototype/test/index.html` — старая главная для визуального сравнения.
- `docs/pages/home.md` — page brief новой главной.
- `docs/pages/service-template.md` — общий каркас коммерческих страниц услуг.
- `docs/pages/web-development.md` — page brief первой страницы разработки.
- `docs/pages/seo-promotion.md` — page brief страницы SEO-продвижения.
- `docs/pages/contextual-advertising.md` — page brief страницы контекстной рекламы.
- `docs/pages/complex-marketing.md` — page brief страницы комплексного
  интернет-маркетинга.
- `docs/pages/about-company.md` — page brief страницы «О компании».
- `docs/pages/blog.md` — общий page brief каталога, детальной статьи и профиля
  автора.
- Старый Next.js static export нельзя нормально редактировать: исходников React/Next.js в репозитории нет. Его файлы сохранены только для маршрута `/test/`.
- Остальные внутренние страницы проектируются с нуля по общему шаблону и
  собственным page brief.
- Новая главная — рабочая гипотеза, которую можно свободно сокращать и перестраивать после просмотра.

Четыре основные услуги — разработка сайтов, SEO-продвижение, контекстная реклама
и комплексный интернет-маркетинг — используют общие токены и повторно
используемые компоненты. Полная последовательность страницы не копируется:
каждая услуга получает от двух до четырёх собственных центральных UX-модулей и
свой page brief.

Блог использует модель hub-and-spoke: `blog/` является хабом, каждая статья
ссылается обратно на каталог, на своего автора и ведёт только на релевантную
услугу. Профиль автора содержит основную информацию и только фактически созданные
материалы. На desktop крупный `h2` статьи закрепляется слева только в пределах
собственной главы; текст читается справа. На mobile глава становится одной
колонкой без дублирования заголовка и без scroll-jacking.

Каталог не выделяет отдельный «главный» материал: все статьи используют одну
карточку. Рабочая пагинация показывает по шесть карточек, хранит номер в
`?page=N`, совместима с фильтром `?category=...` и оставляет весь контент видимым
без JavaScript.

Страница «О компании» использует общую оболочку и визуальный язык сайта, но
строится как самостоятельный редакционный рассказ. Её первый экран всегда
одноколоночный и содержит только утверждённый `h1` на нейтральном светлом фоне —
без фотографии, надзаголовка, подзаголовка, CTA и параллельной правой колонки.
Фотографии команды показываются отдельной управляемой лентой ниже hero.
Центральные элементы страницы — линейная история компании и крупный открытый
блок команды.

По прямому решению пользователя визуальный язык старой главной выбран рабочим
направлением прототипа. Главную пересобираем на чистых HTML, CSS и vanilla JS,
используя узнаваемые принципы первой версии: Unbounded и Manrope, тёплый
бело-кремовый фон, приглушённый сине-серый акцент, круглые кнопки, крупные радиусы,
тонкие тёплые обводки и тёмные выделенные карточки. Это направление для прототипа,
а не финальная дизайн-система.

Композиционный референс для новой главной — опубликованная первая версия
`https://imperil03.github.io/a1/prototype/` и её локальная копия в `/prototype/test/`.
Шапку, ритм первого экрана, вертикальную композицию заголовков, сетки карточек,
нижний CTA и футер воспроизводим по этому референсу. Тексты и порядок разделов
берём только из согласованных источников.

Обязательное правило для всех страниц:

- на первом экране коммерческой страницы услуги единственный `h1` оформлять как
  компактный верхний лейбл; крупный маркетинговый слоган под ним сохранять
  обычным текстовым блоком без `h1`–`h3` и без `role="heading"`;
- точные формулировки `h1`-лейбла и маркетингового слогана брать из page brief
  конкретной услуги; главная страница этому правилу не подчиняется;
- над `h2` не добавлять декоративные рубрики, eyebrow-подписи и пояснения, если их
  прямо нет в согласованном контенте;
- вводный текст раздела ставить сразу под `h2` в той же колонке;
- вводный текст можно ограничить по ширине для чтения, но нельзя переносить в
  отдельную правую колонку;
- у подчёркнутых текстовых ссылок на всех страницах при наведении убираем
  подчёркивание, сохраняя цветовой или другой визуальный отклик и видимый фокус;
- на всех актуальных страницах прототипа название компании пишем только как
  «A1-Интернет Эксперт»; домен, адрес почты и архивный маршрут `/test/` этому
  правилу не подчиняются;
- служебные сообщения о статусе прототипа не показывать посетителю страницы без
  прямой просьбы пользователя.

Для главной действует утверждённая карта блоков:

- первый экран, услуги, системный подход, преимущества, этапы, отрасли и команда —
  из Word-документа с учётом более поздних прямых правок пользователя;
- шесть кейсов и шесть отзывов — дословно из первой опубликованной версии;
- сертификаты и клиенты — один раздел с двумя подгруппами: сертификаты и
  рейтинги показываем одной медленной автолентой, клиентов — статичной сеткой;
- отзывы — отдельный ручной слайдер без автопрокрутки и видимой горизонтальной
  полосы; основное управление — стрелками;
- FAQ состоит из пяти вопросов из Word-документа и трёх вопросов из первой
  версии, всего восемь;
- нижний блок — CTA без формы, его содержание и футер берём из первой версии.

Прямые правки от 29 июля 2026 года:

- H1: «Разрабатываем сайты и продвигаем бизнес в интернете»;
- основной CTA первого экрана ведёт в Telegram;
- у кейсов новая вводная фраза, карточки кейсов не меняются;
- в системном подходе используется «Помогаем им принять решение» и новый итоговый
  абзац;
- сразу после кейсов идут объединённые преимущества и команда;
- внутри объединённого раздела сначала показываем цитату директора в композиции
  первой версии, затем горизонтальный слайдер из шести карточек сотрудников с
  двухуровневой подписью «имя → должность»;
- после раздела «Как проходит работа над проектом» идёт системный подход «Сайт,
  продвижение и аналитика должны работать как единая система».

Проверки выполняем поэтапно:

- после небольших согласовательных правок проводим только быструю проверку
  изменённых фрагментов и синтаксиса;
- не запускаем после каждой итерации полный браузерный прогон всех разрешений,
  маршрутов и интерактивных состояний;
- большую проверку desktop, mobile, доступности, консоли и `/test/` проводим
  один раз после утверждения структуры главной либо по прямой просьбе пользователя.

### Приоритет источников видимого текста

1. Последнее прямое указание пользователя.
2. Источник, который пользователь назначил конкретному блоку.
3. Дословный утверждённый текст и карта источников в page brief.
4. Повторно используемый источник, прямо разрешённый page brief.

HTML любой страницы не является источником текста. Нельзя добавлять,
перефразировать или сохранять видимую фразу, если её нельзя сопоставить с одним
из источников выше. Для главной отдельная карта Word-документа и первой версии
зафиксирована в `docs/pages/home.md`. Производственный сайт
`https://a1-reklama.ru/` можно использовать для исследования и идей, но его текст
не переносится без прямого решения пользователя. На этапе прототипа проверка
каждой рабочей цифры не нужна.

Технический путь статического прототипа не фиксирует production URL, canonical,
редиректы или будущую индексируемую структуру.

## 4. Жёсткие технические ограничения

- Только чистые HTML, CSS и при необходимости небольшой vanilla JS.
- Никаких React, Next.js, Vue, Tailwind, shadcn/ui, GSAP, Motion и других фреймворков или UI-библиотек.
- Не добавлять `package.json`, сборщик и npm-зависимости без нового прямого решения пользователя.
- HTML должен оставаться читаемым и редактируемым вручную.
- JS нужен только для поведения, которое нельзя показать средствами HTML/CSS.
- Прототип должен работать как статический сайт.

## 5. Прототип — не дизайн

Прототип обязан показать:

- цель страницы и поисковый интент;
- иерархию заголовков;
- последовательность блоков;
- смысл и примерный объём контента;
- CTA и путь к обращению;
- места для кейсов, цифр, отзывов и других доказательств;
- внутренние ссылки;
- порядок блоков на мобильном;
- примечания дизайнеру там, где без них возможна неверная трактовка.

Прототип не должен фиксировать финальные:

- спецификации палитры и типографики для production;
- иллюстрации;
- декоративные эффекты;
- анимацию;
- сложную сетку;
- дизайн-систему.

Рабочая стилизация должна следовать выбранному направлению старой главной, чтобы
сравнение `/prototype/` и `/prototype/test/` было осмысленным. Дизайнер вправе
доработать палитру, типографику и компоненты после утверждения структуры.

## 6. Рабочие данные прототипа

На этапе прототипа разрешены правдоподобные рабочие данные:

- телефоны, адреса и офисы;
- возраст компании и размер команды;
- клиенты, кейсы, отзывы и показатели;
- рейтинги, награды и партнёрские статусы;
- цены, сроки, гарантии и результаты.

Они нужны, чтобы проверить структуру, объём блоков, акценты и пользовательский сценарий. Не останавливать работу ради подтверждения каждой цифры или формулировки.

Не добавлять на страницу общие плашки «это прототип», «рабочие данные» или
«пример», если пользователь прямо их не запросил. Контекст для команды хранить в
документации или HTML-комментариях, не в пользовательском интерфейсе.

`docs/facts-register.md` хранит контекст и список данных для будущей проверки, но не ограничивает прототипирование. Фактчек и замена рабочих данных проходят отдельным этапом перед публикацией сайта.

## 7. SEO для Сургута и Тюмени

- Сургут — действующий домашний рынок.
- Тюмень — рынок выхода. В прототипе можно показать гипотетический офис, контакт, команду или локальный кейс, если это помогает проверить структуру страницы.
- Не создавать страницы, где меняется только название города.
- Страница города или комбинация «услуга + город» появляется при отдельном поисковом интенте и собственной содержательной задаче.
- Для Тюмени можно заложить рабочие локальные кейсы, отзывы, партнёров и другие блоки. Перед публикацией их заменят реальными материалами.
- Учитывать Яндекс, Яндекс Бизнес/Карты и 2ГИС, а не только Google Business Profile.
- Точная URL-модель утверждается после SERP-анализа; текущая гипотеза описана в `docs/seo-architecture.md`.

## 8. Порядок работы над страницей

До HTML создать или согласовать короткий page brief:

1. задача страницы;
2. аудитория;
3. основной и дополнительные интенты;
4. регион;
5. главное целевое действие;
6. доказательства;
7. структура секций;
8. внутренние ссылки;
9. рабочие данные и материалы, которые понадобятся в финальной версии;
10. критерии готовности.

После этого:

1. собрать смысловой wireframe;
2. проверить SEO-логику и отсутствие doorway-паттернов;
3. проверить мобильный порядок;
4. согласовать структуру с пользователем;
5. только затем полировать тексты и HTML.

## 9. Навыки и приоритет правил

Полный список и ограничения — в `docs/skills.md`.

При конфликте использовать такой приоритет:

1. прямое решение пользователя;
2. задача и логика прототипа;
3. SEO и информационная архитектура;
4. ограничения прототипа;
5. UX и доступность;
6. русская редактура;
7. согласованное визуальное направление прототипа;
8. остальные визуальные рекомендации — только на будущей дизайн-фазе.

Платные API, MCP-сервисы, SEO SaaS, внешняя отправка данных и массовая публикация запрещены без отдельного разрешения пользователя.

## 10. Критерии готовности

Страница готова как прототип, если:

- её задача понятна без визуального оформления;
- один `h1`, логичная иерархия `h2`–`h3`;
- каждый блок помогает интенту или конверсии;
- все CTA ведут к понятному следующему шагу;
- рабочие цифры, кейсы и контакты помогают понять будущий контент;
- понятен объём материалов для финальной версии;
- предусмотрены desktop и mobile;
- навигация и ссылки логичны;
- HTML семантичен, интерактив доступен с клавиатуры;
- дизайнер поймёт структуру без устного пересказа.

## 11. Работа с файлами и Git
